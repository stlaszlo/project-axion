# Threat Model

## Scope and Method

This threat model covers the path from initiating intent through agent reasoning, authorization, tool invocation, and result handling. It assumes that prompts, retrieved content, models, agent runtimes, tools, credentials, dependencies, operators, and external services can fail or be compromised.

The table is practical rather than exhaustive. Controls reduce likelihood or impact; they do not prove that an action is safe. Residual risks require organization-specific assessment based on data sensitivity, action reversibility, exposure, and operational maturity.

## Threats and Controls

| Threat | Attack path | Consequence | Controls | Residual risk |
|---|---|---|---|---|
| Direct prompt injection | A user instructs the model to ignore constraints, misrepresent intent, or invoke an unauthorized tool | Unauthorized or misleading action proposal | Treat model output as untrusted; schema validation; deterministic authorization; allow-listed capabilities; approval for high-impact actions | The model may still produce harmful proposals that fall within granted authority |
| Indirect prompt injection | Malicious instructions are embedded in retrieved documents, web pages, tickets, tool results, or memory | Agent changes plan, discloses data, or requests an attacker-chosen action | Provenance and classification; isolate instructions from content; least-privilege retrieval; authorize each action; sanitize result release; restrict egress | Detection and content separation are imperfect; authorized data may manipulate reasoning |
| Confused deputy | An attacker causes an agent with broader access to act on resources the attacker cannot access | Privilege misuse through a legitimate agent | Preserve initiator, agent, and workload identity; intersect authority; resource-bound delegation; target authorization | Complex delegation or legacy targets may obscure the initiating actor |
| User/agent identity conflation | Downstream calls use only the user's token or a shared service identity | Loss of attribution, excessive privilege, and weak containment | Distinct identities; actor-chain claims; token exchange; per-workload identity; correlated audit | Some downstream services cannot interpret delegation chains |
| Credential theft | Tokens appear in prompts, logs, memory, tool output, process state, or a compromised runtime | Attacker reuses authority outside the approved path | Broker-side secret resolution; short-lived audience-bound credentials; workload binding; redaction; rotation; network controls | Valid credentials may be abused within their lifetime and scope |
| Delegation expansion | An agent or intermediary changes scope, target, duration, or delegate while forwarding work | Authority exceeds the initiator's grant | Signed/bound delegation; non-increasing scope; deterministic validation at each hop; expiry; chain audit | Cross-vendor delegation semantics may be inconsistent |
| Policy bypass | A tool or target is reachable without the PEP, or an alternate protocol avoids enforcement | Actions execute without Axion authorization | Network and service topology forcing broker use; target-side verification; deny direct credentials; enforcement coverage tests | Misconfiguration or shadow integrations may create bypass paths |
| Policy manipulation | An attacker changes policies, attributes, capability definitions, or trust configuration | Persistent permission expansion or denial of service | Control-plane separation; strong admin authentication; review/approval; signed versions; change audit; rapid rollback | Authorized administrators or compromised control-plane systems remain high impact |
| Stale policy or revocation | Cached decisions, attributes, keys, or sessions outlive a security change | Revoked authority continues temporarily | Bounded cache lifetime; decision expiry; revocation checks; event propagation; fail closed after maximum age | Distributed revocation cannot be instantaneous; availability trade-offs remain |
| Malicious or compromised tool | A tool lies about behavior, changes after registration, exfiltrates input, or returns hostile content | Data loss, unintended external effects, or subsequent prompt injection | Capability registry; version pinning and provenance; sandboxing; egress control; input minimization; output classification; kill switch | Third-party behavior and updates cannot be fully verified |
| Tool parameter manipulation | The model, user, or adapter inserts hidden, ambiguous, or overbroad parameters | Operation affects unintended resources or scope | Strict schemas; canonicalization; reject unknown fields; parameter policy; request digest; target validation | Semantic ambiguity and target-specific interpretation may persist |
| Excessive agency / action chaining | Many individually allowed steps combine into a harmful outcome | Cumulative data extraction, spend, change, or lateral movement | Budgets; rate and volume limits; cumulative-risk policy; bounded plans; reauthorization; approval thresholds; interruption | Harmful combinations may not be known in advance |
| Replay or duplicate execution | An approved request, credential, callback, or message is replayed | Duplicate payment, change, or notification | Nonces; expiry; idempotency keys; single-use grants; channel binding; broker state | Not all external operations support idempotency or reliable deduplication |
| Approval substitution or fatigue | The request changes after approval, the UI hides material facts, or repeated prompts induce careless consent | Human approval authorizes a different or poorly understood action | Bind approval to canonical request digest; clear consequence display; expiry; material-change detection; separation of duties | Humans can still misunderstand, collude, or approve malicious requests |
| Result/data exfiltration | Sensitive API results are returned to an unauthorized user, model provider, memory store, or external tool | Confidentiality breach and regulatory impact | Result-release authorization; field filtering; classification; tenant isolation; model/data routing policy; DLP as a supporting control | Classification and DLP may miss sensitive or inferable information |
| Memory poisoning or cross-session leakage | Attacker-controlled or misclassified content is stored and retrieved across users or tenants | Persistent manipulation or disclosure | Tenant/session isolation; provenance; write policy; retention and deletion; integrity metadata; retrieval authorization | Poisoned but authorized content may remain persuasive |
| Workload or runtime compromise | Agent host, container, plugin, or dependency is exploited | Theft of runtime authority, tampering, or bypass | Workload identity; sandboxing; patching; minimal images; egress restriction; short-lived credentials; attestation where justified; quarantine | A compromised workload can act within its current legitimate envelope |
| Model or dependency supply-chain compromise | Model weights, hosted model behavior, libraries, adapters, or tool packages are maliciously altered | Systematic misreasoning, exfiltration, or unsafe proposals | Provenance; signed artifacts; pinned versions; evaluation; staged rollout; change monitoring; external enforcement | Subtle compromise may evade testing while producing policy-compliant harm |
| Cross-tenant confusion | Tenant identifiers or resource references are omitted, inferred, or swapped | One tenant accesses or modifies another tenant's resources | Tenant-bound identity and credentials; explicit resource identifiers; policy checks; partitioning; negative tests | Shared infrastructure defects can defeat logical isolation |
| Audit tampering or omission | A component drops, alters, floods, or selectively records events | Actions become untraceable; detection and accountability fail | Append-oriented integrity controls; restricted writers; correlation and sequence checks; independent collection; alert on gaps | External systems may provide incomplete evidence; logging outages affect availability choices |
| Audit data leakage | Prompts, payloads, credentials, personal data, or business data are over-recorded | Secondary confidentiality breach and compliance exposure | Data minimization; secret exclusion; field-level access; encryption; retention limits; audited queries | Investigative usefulness conflicts with minimization |
| Availability attack | An attacker exhausts model, policy, broker, approval, API, or telemetry capacity | Denial of service or pressure to bypass controls | Quotas; isolation; backpressure; circuit breakers; capacity planning; fail toward less capability; pre-defined degraded modes | Strict failure behavior may reduce business availability |
| Unsafe failure or fallback | A dependency error triggers broader credentials, default allow, unbrokered access, or skipped logging | Failure increases privilege or hides actions | Explicit deny defaults; no shared-credential fallback; tested failure modes; bounded emergency procedures | Operators may introduce manual bypasses during incidents |
| Irreversible or non-compensable action | An authorized request triggers an action that cannot be undone or interrupted | Permanent financial, legal, safety, or operational impact | Prohibition or high assurance tier; simulation; dual approval; limits; delayed execution; target-native safeguards | Authorization cannot guarantee correctness; some consequences remain irreducible |
| Agent-to-agent trust abuse | A peer agent asserts false identity, context, results, or delegated authority | Lateral movement, poisoned decisions, or privilege expansion | Mutual authentication; explicit delegation; capability allow lists; provenance; reauthorization at each action; bounded message schemas | Interoperability standards and transitive trust remain immature |
| Telemetry-driven automated overreaction | An inaccurate detector initiates containment or remediation | Legitimate work is disrupted or resources are changed incorrectly | Treat detections as input; deterministic response policy; confidence tiers; bounded automation; approval for high-impact remediation | Deterministic policy can faithfully enforce a poor response rule |

## Risk Treatment Notes

- Authorization controls whether an action may occur; they do not establish that the proposed action is factually correct.
- Prompt-injection controls are expected to be imperfect. The primary containment is to keep authority outside the model and constrain every execution path.
- Legacy targets with shared credentials, coarse scopes, or weak audit may be incompatible with higher-risk use cases even when brokered.
- Residual risk grows with irreversibility, autonomy duration, reachable data, credential breadth, cross-organizational delegation, and the number of chained actions.

## Open Questions

- What action-risk taxonomy should determine approval, authentication, isolation, and evidence requirements?
- How should cumulative and emergent risk across action chains be modeled and tested?
- What minimum assurance is required before registering a third-party MCP server or agent-to-agent peer?
- Which attack simulations and enforcement-coverage tests should become release gates?
- When should an inability to produce complete audit evidence block an otherwise authorized action?
